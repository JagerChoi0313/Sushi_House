## 一、算法逻辑 BUG

按「会不会真的错给用户看」排序。**P0 = 会让用户看到错误结论；P1 = 特定输入下错；P2 = 口径不一致/可维护性。**

### A1【P0】过敏患者会被推荐到含过敏原的菜 —— 推荐阶段完全不看日文过敏原表

**位置**：`backend/src/recommend.js:106`
```js
if (tags.some((t) => prefType.get(t) === 'avoid' || prefType.get(t) === 'allergy')) continue;
```
这一行只看 `dish_tags`（中文 18 个标签），**从未读过 `dish_nutrition.allergen_list`**（日文 28 品目）。两套词表互不相通（见 `frontend/common/allergens.js:1-7` 的注释自己也承认了）。

**实测（demo 用户：牛奶过敏 + 牛油果忌口）**：
```
预算×上限 5×4 = 20 组、三套策略共 60 个篮子，去重后被推荐到的「日文标注含乳」的菜：
  - 千層蛋糕 (id=384)  中文标签只有「鸡蛋/小麦」，日文 allergen_list = 乳,卵,小麦
```
根因链：`千層蛋糕` 的中文 tag 是 `鸡蛋 / 小麦` → 不含「乳制品」(tag 6) → 过敏过滤器放行 → 进了候选集 → 被 3c 当成「密度不错」的菜装进篮子。

**为什么现在没炸**：前端 `record.vue` 的「这一单可能含有（日本 28 品目推断）」会兜住——但那是**下单之后**才知道，且是软提醒。推荐页没有任何提示。

**修法**（不动库）：候选集过滤处追加一条，用 `dish_nutrition.allergen_list` 与用户过敏项的中文名做映射比对。映射表 `ALLERGEN_ZH` 已经存在（`frontend/common/allergens.js`），把它复制/共享到后端即可。约 20 行。

### A2【P0】「用餐提示」徽章会说「未命中」，同屏却写着「可能含有乳制品」

**位置**：`frontend/pages/record/record.vue` 的 `allergyHits` 与 `orderAllergens` 两个 computed

同一个界面里：
- 徽章区（`allergyHits`）只看中文 tag → 判「未命中」→ 绿字「已选 N 道，都没有命中你设置的忌口与过敏项。」
- 下方（`orderAllergens`）看日文 allergen → 列出「这一单可能含有：乳制品」

**实测**：在售含「乳」（日文标注）**27 道**，其中中文 tag 也标了乳制品的只有 **17 道**。剩下 **10 道会触发这种自相矛盾**：
```
id 210 全栗以赴焦糖千層交響曲   乳,卵,小麦   中文tag: 无命中
id 213 豪華花之戀            さけ,乳,大豆  中文tag: 无命中
id 377 / 437 可爾必思水語      乳          中文tag: 无命中
id 384 / 429 千層蛋糕        乳,卵,小麦   中文tag: 无命中
id 430 焦糖千層蛋糕          乳,卵,小麦   中文tag: 无命中
id 431 特製脆片巧克力蛋糕      乳,卵,小麦   中文tag: 无命中
id 433 草莓香草聖代          乳,卵        中文tag: 无命中
id 434 芒果雪花冰            乳          中文tag: 无命中
```
**对过敏用户来说，这是最危险的一类 bug**：绿色徽章给出「安全」的错觉，而真实风险在下面被折叠成小字。

**修法**：徽章判定改为「中文 tag 命中 **∪** 日文 allergen 命中」，两边任一命中就标红；或干脆把徽章拆成两个（「你的忌口」/「菜品标注过敏原」），别用一个绿色 `未命中` 笼统收尾。

### A3【P1】热量下限 > 上限时被静默改写，用户填的数消失

**位置**：`backend/src/recommend.js:66-71`
```js
calTarget = calMin == null ? Math.round(calLimit * 0.8) : Math.min(Math.round(calMin), Math.round(calLimit));
```

**实测**：
| 用户填 | 返回 | 界面第 143 行显示 |
|---|---|---|
| 下限 800 / 上限 400 | `calorieMin=400, calorieLimit=400` | 「· 目标 **400**」，填的 800 不见了 |
| 下限 1000 / 上限 500 | `calorieMin=500, calorieLimit=500` | 「· 目标 **500**」 |

`Math.min()` 把越界的下限夹成上限，**没有任何报错或提示**。用户以为自己要 800，看到的是 400。

**修法**：`calMin > calLimit` 时返回 400 且消息写明「下限不能大于上限」；或前端在提交前校验。两行。

### A4【P1】返回字段 `calorieMin` 语义漂移：它是「内部目标」，不是「用户填的下限」

**位置**：`recommend.js:361-388` 返回 `calorieMin: calTarget`

`calTarget` 有三重来源混在一个字段里：
1. 用户填了下限 → `min(用户下限, 上限)`（基本等于用户填的）
2. 用户**没填**下限、只填上限 → `Math.round(上限 × 0.8)` ← **凭空造出来的数**
3. 用户什么都没填 → `null`

**实测**：只填上限 800 → 返回 `calorieMin = 640`，界面渲染成「热量 800 / 上限 800 kcal（100%）· **目标 640**」。用户从没说过 640，界面上却把它当「目标」展示。

配合 `plan.vue:53` 的提示语「下限留空时按上限的 80% 去凑」——而实际凑到了 **100%**（因为 3b 补到 `fillTo` 而非 `calTarget`）。**提示语与行为相反**。

**修法**：拆成两个字段 `calorieMinUser`（原样回显）与 `calorieTarget`（内部用），界面只展示用户给过的数；提示语改成「下限留空时会把上限当目标去凑」。

### A5【P1】「均衡」策略宣称 90%，实测到 93–100%

**位置**：`recommend.js:74` `fillTo = Math.round(calLimit * 0.9)`，但 3b 之后的**步骤 4 补份**与 3c 的 `buildByDensity` 都用 `calLimit` 或 `fillTo` 不一致的封顶，且 `calorieFill` 的分母是 `calLimit` 而不是 `fillTo`。

**实测**（上限 1000，均衡档）：
| 预算 | 目标 900（90%） | 实得 | fill 显示 | 超出目标 |
|---|---|---|---|---|
| 80 | 900 | **930** | 93% | +30 |
| 120 | 900 | **995** | **100%** | +95 |
| 200 | 900 | 980 | 98% | +80 |

用户看到的「100%」其实是「贴住了上限」，而策略承诺的是「补到上限的九成」。**界面文案与实际行为对不上**。

**修法**：`calorieFill` 的分母按策略取（均衡用 `fillTo`），或文案改成「补到上限附近，均衡档约为九成」。

### A6【P1】`goalBlockedCount` 在去重之前计数，文案把重复菜算成两道

**位置**：`recommend.js` 候选集循环里 `goalBlockedCount++` 发生在 `seenName` 去重**之前**。

**实测**：
| 目标 | `goalBlockedCount` | 其中唯一菜名 | 界面上写的 |
|---|---|---|---|
| 减重（排油炸） | **27** | **18** | 「按「油炸」标签排除了 27 道菜」 |

**修法**：把 `goalBlockedCount++` 挪到 `seenName` 判定之后，或改成统计唯一菜名。

### A7【P2】3c「整篮重排」会整篮丢掉用户偏好，只看热量密度

**位置**：`recommend.js:240-289`，触发条件 `totalCal < calLimit * 0.8`
```js
if (alt.cal > totalCal) { /* 整篮替换 */ }
```
替换条件**只比较热量**，不看 `score`（偏好分）、不看 `dislikeHit`。

**实测**（demo 喜欢三文鱼/虾/鲜，讨厌咸）：
| 预算/上限 | 结果 |
|---|---|
| ¥40 / 1500 | 天婦羅綜合拼盤 ×1 + 抹茶 ×2（**零偏好命中**） |
| ¥40 / 1200 | 牛肉烏龍麵 ×1 |
| ¥60 / 2000 | 茶碗蒸 / 鮭魚 / 天婦羅綜合拼盤 / 地瓜薯條 / 小黃瓜卷 |

¥40/1500 这组是最极端的：用户花 34 元、拿到 1500 kcal、**一道他喜欢的菜都没有**，其中「天婦羅綜合拼盤」是油炸（如果同时开了「减重」目标，它反而会被 goal 过滤掉 → 两个目标打架）。

**修法**：整篮替换加一条「新篮子的偏好分不得低于旧篮子」，或改成「按密度装篮时用 score 做次级排序」。

### A8【P2】儿童模式的「甜味优先」是死代码（与控糖同时开启时）

**位置**：`recommend.js` `KID_BONUS = [15]`（甜）在 `goal` 的 `blood_sugar` 过滤（同样 tag 15）**之后**执行。

**实测**（预算 100 / 上限 800 / kidMode + 控糖）：

茶碗蒸, 黄瓜卷, 鮭魚, 鮭魚腹, 炙烤鮭魚肚, 蘿蔔泥炙烤鮭魚肚, 炙燒明太子鮭魚, 赤蝦, 乌龙茶

### A9【P2】`prefRatio` 在「用户没设过任何偏好」时默认 0.5，白送 10 分

**位置**：`evaluate.js:78` `const prefRatio = prefTotal > 0 ? likeHit / prefTotal : 0.5;`

- 从没设置偏好的用户 → `prefTotal = 0` → `+10 分`
- 设置了偏好但刚好一半不符的用户 → `prefRatio = 0.5` → 也是 `+10 分`

两者待遇完全相同，而「没数据」不等于「一半符合」。同理 `dislikeHit * 3` 没有封顶，10 道菜全踩雷扣 30 分（`dislike` 只是口味，不是健康风险）。

**修法**：`prefTotal === 0` 时这一项按 0 计（不奖不罚），并在 `basis` 里标注 `prefCountMode: 'no-preference'`。

### A10【P0-公平性】评级上限对「有计划」和「没计划」的一餐不公平

**位置**：`evaluate.js:95-107`

```js
let score = 60;
// budgetMet、calorieMet 只在有 plan 时才不是 null
if (budgetMet === true) score += 15;
if (calorieMet === true) score += 15;
score += prefRatio * 20 - dislikeHit * 3;
```

| 场景 | 理论最高 | 现有实测 |
|---|---|---|
| **没有关联计划**（手记一餐） | 60 + 20 = **80** | 4 条记录全 ≤ 80（77 / 80 / 80 / 80） |
| **从推荐计划点进来** | 60 + 15 + 15 + 20 = 110 → **clamp 100** | 我测的那条 = **100（夯）** |

即「同样吃得很好」，从推荐计划走就比手记多 **20 分空间**，足以跨两个档位（顶级 75 → 夯 90）。而用户根本不知道这个差异存在。

**证据**：`meals` 表 6 条记录里，`plan_id` 非 null 的只有 1 条（我测试建的），分数 100；其余 plan_id 全 null，全部 ≤80。

**修法**：要么没有计划时也按「未设目标 = 达成」给分（不该因缺数据受罚），要么把预算/热量两项的总权重降到与口味项同量级，别让「有没有用推荐」决定档位。

### A11【P2】`confirmMeal` 四步写库没有事务

**位置**：`evaluate.js:258-272`
```js
UPDATE meals SET status='confirmed'
→ evaluateMeal（INSERT meal_evaluations）
→ recomputeProgress（DELETE user_dish_progress WHERE user_id=? + 重建）
→ awardBadges
```
**全项目 `grep -E 'BEGIN|COMMIT|ROLLBACK|transaction'` = 0 命中**。

任何一步抛错都会留下不一致状态：
- 第 2 步失败 → 状态已 confirmed、评级没写 → `mealDetail` 显示「评级为空」
- 第 3 步失败 → 图鉴先被 DELETE 清空、没重建 → **用户所有解锁进度清零**

**修法**：`db.exec('BEGIN')` … `db.exec('COMMIT')`，catch 里 `ROLLBACK`。node:sqlite 支持同步事务，约 15 行。

## 二、人文需求审计

按「弱势用户会不会受伤」排序。

### B1【严重】过敏提示存在「绿色误报」，风险被界面主动掩盖

见 A2。对食物过敏者，「未命中」三个字是**明确的授权信号**，而真实风险在下面变成灰色小字。这已经不是文案问题，是把高风险结论用低风险样式呈现。

**建议**：过敏这类不可逆风险，界面不允许出现「未命中」这种否定式绿灯；只能出现「中文标签未命中（可能不完整，请看下方标注）」。

---

### B2【严重】热量与过敏原全是推断值，但主界面看不出来

**数据层写得非常清楚**：`dish_nutrition.disclaimer` = 「热量与过敏原为程序推断，非官方标示」，`allergen_source` = 「程序推断：菜名关键词 → 日本食品表示法28品目 + USDA FoodData 热量」。

**前端只在一处提到**：`menu.vue:85` 详情弹层的「热量/过敏原为推断值」。

**但列表卡片上**：`menu.vue:58` 直接写 `· 245 kcal`，**无任何限定**。推荐结果卡 `plan.vue:106/133/142` 也直接写「XXX kcal」。全前端 `grep '估算|推断|非官方'` 在 `pages/*.vue` 里是 **0 命中**（只有 menu 那一处用了 `'热量/过敏原为推断值'` 这个字符串，不含这些词）。

对**糖尿病 / 减重 / 肾病**用户，一个「推断值」和一个「官方标示」的决策权重完全不同。现在它们长得一模一样。

**建议**：列表卡片的热量加一个 `≈` 或上标；推荐结果卡首次展示时给一行「热量为按菜品构成推算，误差可能在 ±20%」。

---

### B3【严重】用户没有任何删除自己数据的入口 —— 隐私与「被遗忘权」

**实测**：45 条路由里 `DELETE` 只有 4 条，全部是 admin 删菜品/分类/标签/勋章规则：
```
/api/admin/dishes/:id   /api/admin/categories/:id
/api/admin/tags/:id     /api/admin/badge-rules/:id
```
用户**无法删除**自己的：
- 用餐记录（只能「作废」，记录还在库里）
- 上传的账单照片（`meal_uploads` 只有插入，没有删除）
- 推荐计划（505 条，只能堆着）

而 `uploads/` 是**静态目录、无鉴权**：
```
GET /uploads/001_1776323a.png（无 token）→ 200 image/png
```
文件名是 `Date.now()_random6.png`，猜到不容易，但**一旦泄露（截图、分享链接、日志）就永久公开**，且用户没有撤回手段。

**建议**：① 给 `/uploads/*` 加基于 `meal_uploads.user_id` 的会话校验；② 提供「删除我的记录 / 删除这张照片」，物理删或至少标记不可见。

### B4【中】评级档位用词带贬损色彩

`evaluate.js:4-13`：
```js
{ key: 'hang',  min: 90, label: '夯' }
{ key: 'top',   min: 75, label: '顶级' }
{ key: 'elite', min: 60, label: '人上人' }
{ key: 'npc',   min: 40, label: 'NPC' }
{ key: 'lame',  min:  0, label: '拉完了' }
```

「NPC」「拉完了」是网络贬义词。对一个**记录自己吃饭**的应用，把用户的日常饮食评价成「NPC」「拉完了」，属于把娱乐化表达强加给不想要它的人。而且这个评级**无法关闭**、会出现在历史列表、首页「最近用餐」和详情页。

叠加 A10 的公平性问题：手记一餐的上限是 80 分（顶级），想吃出「夯」必须先走推荐——**评级实际上在引导用户按推荐点单**。

**建议**：① 换成中性档位（很好 / 好 / 一般 / 偏多 / 偏少）；② 提供「不显示评级」开关；③ 至少把「NPC/拉完了」换掉。

### B6【中】无任何无障碍语义

`grep 'aria-|role='` 在 11 个页面 + `App.vue` 里 **0 命中**。全部交互都是 `<view @tap>` 而不是 `<button>`：
- 读屏软件读不出「这是个按钮」
- 底部 tabBar 之外的 `.chip` / `.vacancy` / `.same-btn` 全是裸 view
- 星级评分用 5 个 `<text>★</text>`，没有 `aria-label="4 星"`

小程序对 `aria-role` / `aria-label` 有支持（`aria-role="button"`），加成本很低。

### B7【中】没有「减少动效」开关，第 6 条需求加的三个动画不能关

### 3. 后端没起来时，界面显示「0 道 / 0/0 图鉴 / 没有找到菜品」（会让人以为数据丢了）

演示时最容易翻车的场景不是代码错，是**忘了先起后端**。此时每个请求都失败，
页面把空数组正常渲染出来：菜单显示「没有找到菜品」、图鉴「暂无菜品 0/0」、
首页「0 已确认用餐」。看上去像数据被清空了。

改法两处：

- `frontend/common/api.js`：请求失败统一弹一次 toast「连不上后端，请先启动服务」，
  5 秒内只弹一次（一个页面四五个请求同时失败不会糊一屏），错误信息也写明这一点。
- `frontend/pages/menu/menu.vue` 与 `frontend/pages/encyclopedia/encyclopedia.vue`：
  各加一个 `loadErr` 状态，失败时显示「连不上后端，请先启动服务后下拉刷新」，
  与「真的没有菜品」区分开。

实测：停掉后端后重进菜单页 → 仍显示旧文案（编译缓存问题），清缓存重启后
两页都显示新的「连不上后端」提示；恢复后端 → 12 页体检 12/12 正常、异常 0。
