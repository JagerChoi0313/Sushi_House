## 1. 现状（说清楚，不含糊）

`backend/src/routes.js:571` 的 `ocrImage` 调的是同文件 `:134` 的 `demoRecognize`。它**不是识别**：

```js
const pool = db.prepare("SELECT id, name, price, calories FROM dishes WHERE status='on_sale' AND calories IS NOT NULL").all();
const shuffled = pool.sort(() => Math.random() - 0.5);
const count = type === 'bill' ? 3 : 2;
return shuffled.slice(0, count).map((d) => ({ ..., source: 'mock' }));
```

即：从在售且有热量的菜里随机抽 3 条（账单）或 2 条（菜品），字段照真实结果的形状填好。

**每个条目都带 `source: 'mock'`**，前端 `record.vue` 据此显示「演示数据」的提示。
这是这一版刻意做的区分 —— 让演示能跑通，但不让任何人误以为做了 OCR。

## 2. 接口契约（不得更改）

### 请求

```
POST /api/uploads/:id/ocr
Authorization: Bearer <token>
```

`:id` 是 `POST /api/uploads` 返回的上传记录 id，且必须属于当前用户（否则 404）。

### 响应

```json
{
  "uploadId": 12,
  "type": "bill",
  "items": [ /* 行项目数组，见 §3 */ ]
}
```

侧效应：`meal_uploads` 那一行的 `ocr_status` 置为 `'done'`，`ocr_result` 写入 `items` 的 JSON 字符串。

## 3. 行项目字段（四个必填口径 + 两个扩展）

| 我们的字段 | CORD 对应 | 类型 | 含义 | 可空 |
|---|---|---|---|---|
| `dishName` | `menu.nm` | string | 菜名（识别出来的原文，不要为了匹配而改写） | 否 |
| `quantity` | `menu.cnt` | number | 数量，整数，≥ 1 | 否 |
| `unitPrice` | `menu.unitprice` | number | 单价（元） | 是 |
| `quantity × unitPrice` | `menu.price` | — | 小计（我们不单独存，用时算） | — |
| `unitCalories` | （CORD 无） | number | 单份热量（kcal），来自我们的 `dishes.calories` | 是 |
| `dishId` | （CORD 无） | number | 匹配到的 `dishes.id`；匹配不上就 `null`，由用户手选 | 是 |
| `source` | （CORD 无） | string | `'mock'` \| `'ocr'` \| `'photo'` \| `'manual'` | 否 |

**为什么是这四个字段**：CORD（`clovaai/cord`，496 星，**CC-BY-4.0**）给收据定义的标准行项目就是
`menu.nm / menu.cnt / menu.unitprice / menu.price`，并附带 1 000 张人工标注样本与类别清单。
我们现在的字段与它是**同构**的 —— 也就是说数据结构不需要动，只需要换实现。

## 4. 写一个真实识别器时要满足的不变量

1. **`source` 必须诚实**：演示数据一律 `'mock'`；接了真实 OCR 才允许写 `'ocr'` / `'photo'`。
   `record.vue` 是靠这个字段决定要不要显示「演示数据」提示的 —— 写错就等于对用户撒谎。
2. **`dishName` 保留识别原文**，匹配结果放 `dishId`。不要为了「匹配得上」把菜名改写成我们库里的名字：
   用户核对时看到的是照片上的字，不是我们库里的字。匹配不上时 `dishId: null`，让用户手选。
3. **`quantity` 至少为 1**，`unitPrice` / `unitCalories` 允许为 `null`（照片上被遮挡、或这道菜没有热量记录）。
4. **一次请求只处理一张图**：`items` 是这张图里的所有行项目，不要跨图合并。
5. **不要在没有把握时编造**：识别不出合计就返回 `items: []`，让用户手动加 —— 假行项目比空结果更糟。

## 5. 实现路径（按可行性排序）

### 路径 A：纯本地规则解析（不引依赖，推荐先做）

1. 图片 → 文本：这一步需要 OCR。小程序端没有可用的离线 OCR；
   最省事的做法是**双端降级** —— 有网时调一个 HTTP OCR 服务，没网时直接返回 `items: []` 让用户手填。
2. 文本 → 行项目：**纯字符串处理，与语言无关，可以直接把规则搬过来**，
   参照 `ReceiptManager/receipt-parser-legacy`（856 星，Apache-2.0）的顺序：
   先定位日期/店名 → 逐行匹配「名称 + 数量 + 单价 + 小计」→ 最后找合计/税/支付方式 → 对 OCR 常见错字做容错。
3. 行项目 → `dishes`：拿 `dishName` 在 `dishes` 里做名称相似度匹配（编辑距离或包含关系），
   命中则填 `dishId`，否则留 `null`。

### 路径 B：接现成 OCR 服务

`PaddleOCR`（92 445 星，Apache-2.0）中文效果最好，但**是 Python 服务**。
本项目后端是零依赖 Node（`node src/server.js` 一条命令起），引入 Python 进程会让这个特性消失。
如果确实要接，应作为**独立可选服务**：默认不启动，`/api/uploads/:id/ocr` 检测不到服务时返回 `items: []`。

### 路径 C：云 OCR API

需要密钥与联网。与路径 B 同样作为可选，不写进默认启动路径。

## 6. 怎么评估做得好不好

用 CORD 的 1 000 张标注样本（CC-BY-4.0）算四个字段的准召：

| 指标 | 口径 |
|---|---|
| 行检出率 | 识别出的行数 / 标注行数 |
| 菜名准确率 | `dishName` 与标注 `menu.nm` 完全一致的比例 |
| 数量准确率 | `quantity` 与 `menu.cnt` 一致的比例 |
| 金额准确率 | `unitPrice` 与 `menu.unitprice` 误差 < 0.01 的比例 |
| 匹配命中率 | `dishId` 非空的比例（这个是我们独有的指标） |

> **许可提醒**：CORD 是 **CC-BY-4.0**。只要用了它的样本、类别清单或 schema 定义，就**必须在文档或界面上署名**。
