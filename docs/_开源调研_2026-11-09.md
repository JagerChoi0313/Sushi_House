# 开源调研：能借什么、不能借什么

日期：2026-11-09
调研范围：小程序点餐/UI 组件库、账单 OCR、食物营养数据、汇率 API
星数与许可证：全部走 GitHub API 实测（`docs/_tmp_repos.json` 是原始抓取结果），不是记忆里的数字
边界：本文件只做调研，**未改动任何文件**。凡涉及 `backend/` 或数据库的改动建议，都按 `继续开发说明.md`「零、边界」先说明再动。

---

## 0. 一句话结论

**点餐小程序这个赛道没有高 star 模板**（最高的 `WHaveFun/yipin` 只有 152 个星，且 2020 年底停更）。
高 star 的全都集中在**基础设施**层：UI 组件库、OCR 引擎、营养数据库、汇率 API。

所以「找一套开源点餐小程序抄过来」这条路不通；真正能借的是三样东西 ——
**①把假的账单识别摆到明面上；②用 MIT 营养库补齐 `dishes.calories`（顺带让 BUG-1 自己消失）；③把行项目结构对齐 CORD 的 schema，作为将来接真 OCR 的对接契约。**

## 2. 逐项：能借什么、不借什么

### 2.1 UI 组件库 —— 不借（已在最优解上）

`vant-weapp` 18 473 星，是这个细分里星最高、维护最勤的（2026-10-10 还在推）。
再看另外六个：

- `tdesign-miniprogram` 1 795（**支持 uniapp**）与 `uni-ui` 2 090（DCloud 官方）技术上更贴合 uni-app；
- `weui-miniprogram` 2 435 是官方设计语言，但主色 `#07C160` 与我们现在的深色金棕体系冲突；
- `ant-design-mini` 554 以支付宝为主；
- `coloruicss` 12 355 星虽高，但 **2024-04 停更**，且高饱和彩色与我们的风格相反。

**换库的代价**：`frontend/` 有 11 个页面，全都直接写了 `vant-weapp` 的 `van-switch` / `van-stepper` 与自定义 wxss。换库 = 11 页重写 + 重新适配主题变量 + 重新拍 5 张截图。
**收益**：零（当前库没有已知缺陷）。
→ **不换。** 唯一值得留着备查的是 `tdesign-miniprogram`（支持 uniapp），如果将来要上 PC/多端再说。

### 2.2 点餐模板 —— 不借

`yipin` 152 星 / Apache-2.0 / 2020 年停更，其余三个都在 40 星以下。它们的数据模型是
**商品 → 购物车 → 下单 → 支付**；本项目没有支付链路，「点单卡」是**生成一张图片给人看**，
两者不是同一种东西。借进来只有两种结果：要么整套重写（等于不用它），要么塞进一堆用不到的表。

### 2.3 账单 OCR —— 借「规则」和「schema」，不借引擎

**先说本项目的事实**（见 `_缺陷检查_2026-11-09.md`）：
`backend/src/routes.js:555` 的 `ocrImage` 调的是 `routes.js:124` 的 `mockRecognize` ——
它从 `SELECT id, name, price, calories FROM dishes WHERE status='on_sale' AND calories IS NOT NULL`
里 `Math.random()-0.5` 洗牌取前 N 条（`bill` 取 3、`dish` 取 2），返回带 `source: 'ocr'` 的假结果。
**「拍照识别账单」这个功能目前是假的。**

- `PaddleOCR`（92 445 星）效果最好，但是 **Python 服务**。本项目后端是零依赖 Node（`node src/server.js` 一条命令起），引一个 Python 进程会让这个特性消失。`doctr` 同理。
  → **不借引擎。**
- `receipt-parser-legacy`（856 星）真正值钱的不是它的 tesseract，而是它的**行项目解析规则**：
  先定位日期/店名，再逐行匹配「名称 + 数量 + 单价 + 小计」，最后找合计/税/支付方式，并对 OCR 错字做容错。
  这套顺序是**纯文本处理**，与语言无关，可以直接移植到 Node。
- `cord`（496 星，CC-BY-4.0）是**唯一该借的结构**：它定义了收据行项目的标准字段
  `menu.nm`（名称）/ `menu.cnt`（数量）/ `menu.unitprice`（单价）/ `menu.price`（小计），
  外加 1 000 张标注样本与类别清单，是用来**评估**解析器准不准的。

**好消息**：`mockRecognize` 现在返回的 `{ dishId, dishName, quantity, unitPrice, unitCalories, source }`
与 CORD 的四个字段是**同构**的。也就是说我们不需要改数据形状，只需要把这个映射写成契约。

### 2.4 营养 / 过敏原数据 —— 借 MIT 的那个，避开 AGPL

- `H1an1/health-coach`（66 星，**MIT**，含 600+ 中式食物营养库）→ **可借**。它正好对上 BUG-1 的根因：
  `dishes.calories` 271 道里只有 22 道有值，而 `dish_nutrition.kcal_estimate` 有 249 行。补齐缺的 `calories` 就能让后端的热量上限过滤从「只剩 20 道候选」恢复到应有的 221~237 道。
- `openfoodfacts-server`（1 202 星）**AGPL-3.0**，`wger`（7 246 星）**AGPL-3.0** →
  AGPL 的网络服务条款对「对外提供的小程序」有传染风险。**代码不借。**
  但 Open Food Facts 的 **allergen token 设计**（`en:milk` 这类标准化写法）值得作为「我们该怎么命名过敏原」的参照 —— 记在脑子里，不落文件。
- `mcp-opennutrition`（209 星 MIT）是 MCP server 形态，我们不是 MCP 场景 → 不借。
- `nutrition-facts`（34 星，**无许可证**，2017 停更）→ 不借。

### 2.5 汇率 —— 可以做，但不是第一优先

`frankfurter`（2 078 星 MIT，2026-11-08 还在推）免费、无需 key、数据来自欧洲央行。
现状：世界菜单显示 `NT$40 ≈ ¥9`，说明 `price_cny` 是**预先算好写进库**的。
借它可以改成**后端读时动态换算** —— 这不改库结构，符合「数据库只能加数据」的约束。
但要注意两件事：①汇率波动会让展示数字跳动，观感变差；②断网时必须有兜底，即库里那个预计算值要保留。
→ 值得做，但排在下面三项之后。

## 3. 三个可落地的改造（按性价比排序）

### 改造 1 —— 把「假识别」摆到明面上（零依赖，最高性价比）

**问题**：`routes.js:124` 的 `mockRecognize` 返回 `source: 'ocr'`，前端 `record.vue` 拿到后当成识别结果显示。
用户（和答辩评委）会以为真的做了 OCR。

**做法**（两步，都是小改）：
1. 后端：把 `mockRecognize` 的返回值 `source` 从 `'ocr' | 'photo'` 改成 `'mock'`，函数改名 `demoRecognize`，
   并在函数上方加注释说明「这是演示用示例数据，未接入真实识别」。
2. 前端：`frontend/pages/record/record.vue` 在识别结果区加一行提示「演示用示例数据，尚未接入真实识别」。

**成本**：`backend/src/routes.js` 一个函数 + `frontend/` 一处文案。改完按硬约束跑 `node --check`。
**收益**：消除「把演示当功能」的风险。这不是功能增强，是**把已经存在的边界说清楚**。

### 改造 2 —— 补齐 `dishes.calories`，让 BUG-1 自己消失

**问题**：`backend/src/recommend.js:31-33` 用 `d.calories` 卡热量上限，而这个字段 271 道菜里只有 22 道有值，
导致 cap 从 400 调到 1000，候选永远只有 20 道（按 `dish_nutrition.kcal_estimate` 应该是 221~237 道）。
前端 `frontend/pages/menu/menu.vue:157` 的 `kcalOf(d)` 已经用对口径（先看 `kcal_estimate`，回落 `calories`），后端没跟上。

**做法**（两条路，任选，都不违反硬约束）：
- **A（只补数据，不动代码）**：用 `dish_nutrition.kcal_estimate` 把 `dishes.calories` 的空值**填空**。
  这是「填空字段」，完全符合「数据库只能加数据」。缺的那部分（249 行覆盖 271 道里的 249 道）再用 `H1an1/health-coach`（MIT）的 600+ 中式食物库补。
  改前必须备份到 `database/sushi_house.backup-YYYYMMDD-HHMMSS.db`，改后逐表 `count(*)` + `pragma table_info` 自证只增不减。
- **B（改一行代码）**：`recommend.js:31-33` 改成与前端同一个口径
  （`const kcal = d.kcal_estimate != null ? d.kcal_estimate : d.calories`）。属于 `backend/` 改动，**要先说明再改**，改完 `node --check`。

**建议**：先做 A（数据层修复，零代码风险），B 作为对齐口径的后续。

### 改造 3 —— 把行项目结构对齐 CORD，写成「将来接真 OCR 的契约」

**做法**：在 `docs/` 新增一页，写明

| 我们现在的字段（`mockRecognize` 返回） | CORD 对应字段 | 含义 |
|---|---|---|
| `dishName` | `menu.nm` | 菜名 |
| `quantity` | `menu.cnt` | 数量 |
| `unitPrice` | `menu.unitprice` | 单价 |
| `unitCalories` | （CORD 无，我们自有） | 单位热量 |
| `quantity × unitPrice` | `menu.price` | 小计 |

并注明：CORD 是 **CC-BY-4.0**，将来若真的使用它的样本或类别清单，**必须署名**。

**收益**：现在什么都没接，但把契约先写清楚；等真接 PaddleOCR / 自建解析器时，前后端不需要改数据结构，
只需要换 `routes.js:124` 那一个函数的实现。
