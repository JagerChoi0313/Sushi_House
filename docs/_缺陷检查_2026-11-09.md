## 严重（功能可见错误）

### BUG-1 `recommend.js` 读错热量字段 → 填了热量上限后候选只剩 20 道

- **位置**：`backend/src/recommend.js:31-33`
  ```js
  if (calLimit != null) {
    if (d.calories == null || d.calories > calLimit) continue;
  }
  ```
- **问题**：`dishes.calories` 这一列 271 道里只有 **22 道**有值（`on_sale` 里只有 **20 道**）。真正的热量在 `dish_nutrition.kcal_estimate`（249 行）。所以「热量上限」这个筛选条件把候选集从 269 道砍到 20 道。
- **实测**：

  | 热量上限 | 按 `dishes.calories`（现逻辑） | 按 `dish_nutrition.kcal_estimate`（应为） |
  |---|---|---|
  | 400 kcal | 20 道 | 221 道 |
  | 600 kcal | 20 道 | 231 道 |
  | 800 kcal | 20 道 | 235 道 |
  | 1000 kcal | 20 道 | 237 道 |

  `on_sale` 总数 269 道 → 现逻辑下四条上限的候选一样多，说明**上限根本没起作用，是"有没有录 calories"在决定**。
- **佐证**：前端 `frontend/pages/menu/menu.vue:157` 的 `kcalOf(d)` 已经写成 `d.kcal_estimate != null ? d.kcal_estimate : d.calories`，即前端早就以 `kcal_estimate` 为准；后端推荐器没跟上。
- **影响**：餐前推荐在带热量上限时几乎无法凑出套餐，且热量估算偏低。
- **修法方向**：`generatePlan` 里 join `dish_nutrition` 取 `kcal_estimate`（并保留 `dishes.calories` 兜底）；同时 `meal_plan_items.unit_calories` 的写入值也要跟着换成同一口径。

### BUG-2 评级「口味匹配」恒为 100%

- **位置**：`backend/src/evaluate.js:57-67`
  ```js
  for (const t of tagIds) {
    const p = prefs.get(t);
    if (p === 'like') { likeHit++; likeTotal++; }   // ← likeTotal 只在 like 时自增
    else if (p === 'dislike') { dislikeHit++; }
  }
  ...
  const prefRatio = likeTotal > 0 ? likeHit / likeTotal : likeHit > 0 ? 1 : 0.5;
  ```
  `likeHit` 与 `likeTotal` 永远同步自增 → `likeHit / likeTotal` 恒等于 1。只要命中了任意一个「喜欢」标签，口味匹配就是 100%。
- **实测**：4 条 `meal_evaluations` 的 `basis.prefRatio` **全部是 1**（meal 1/2/3/4），而它们的 `likeHit` 分别是 4/3/2/2、`dislikeHit` 1/0/0/0。
- **附带**：`likeHit > 0 ? 1` 这个分支永远不会走到（`likeTotal === 0` 时 `likeHit` 必为 0），是死代码。
- **影响**：评分里占 20 分的口味项退化成一个常数 20；用户改偏好不会改变评级，测评的"趣味评级"失去区分度。
- **修法方向**：分母应该是「这条记录里出现的、用户**表过态**的标签数」（like + dislike），或者是「用户偏好标签的总数」；两者取哪个要先定口径。

### BUG-3 超预算反而加分（扣分符号写反）

- **位置**：`backend/src/evaluate.js:86-88`
  ```js
  else if (budgetMet === false) {
    score += Math.max(-15, -15 * Math.min(1, -budgetDelta / (plan.budget || 1)));
  }
  ```
  `budgetDelta = round(paid - plan.budget, 1)`，超支时是**正数**；`-budgetDelta / budget` 是负数；`Math.min(1, 负数)` 还是负数；`-15 * 负数` = **正数**；`Math.max(-15, 正数)` 保留这个正数 → **超支越多，得分越高**。
- **举例**：预算 100 实付 150 → `budgetDelta = 50` → 加分 **+7.5**。
- **对照**：同段 `:91` 的卡路里分支 `-15 * Math.min(1, calorieRatio - 1)` 符号是**对的**（超限时 `calorieRatio-1 > 0` → 得负数 → 扣分）。所以这处是笔误，不是设计。
- **为什么现在没暴露**：现有 4 条评级记录的 `basis.plan` 全是 `null`（都没有关联计划），这条分支还没被真实数据走到。
- **修法方向**：`Math.max(-15, -15 * Math.min(1, budgetDelta / budget))`。

### BUG-4 `schema.sql` 缺 4 张表 → 从零建库会建出残库

- **位置**：`backend/schema.sql`
- **实测**：`schema.sql` 里 16 个 `CREATE TABLE IF NOT EXISTS`；实际库 21 张表（去掉 `sqlite_sequence` 是 20 张）。缺的是：

  | 缺失的表 | 库里行数 | 缺了会怎样 |
  |---|---|---|
  | `world_dishes` | 1525 | `/api/world/meta`、`/api/world/dishes`、`/api/world/dishes/:id` 全 500 |
  | `dish_nutrition` | 249 | `/api/dishes` 的 nutrition JOIN 失败，热量/过敏原全空 |
  | `ingredients` | 98 | `/api/ingredients` 500 |
  | `dish_ingredients` | 385 | 菜品→配料关系丢失 |

- **影响**：`node src/init_db.js` 从零建库后，世界菜单、营养、过敏原三块功能直接不可用；但现有库是人肉/脚本补出来的，所以一直没被发现。
- **修法方向**：把这 4 张表的 DDL 补进 `schema.sql`（**只加不改**，不碰现有库）。

### BUG-5 跨地区比价用精确字符串相等 → 441 道永远查不到对照

- **位置**：`backend/src/routes.js:843-856`（`worldDish`）
  ```sql
  WHERE ingredients = ? AND forms = ? AND flavors = ? AND id <> ?
  ```
  参数直接取当前行的 `row.ingredients / row.forms / row.flavors`，其中可能有 `NULL` / 空串。
- **实测**：
  - `world_dishes` 1525 行里，`flavors` 为空的有 **1028 行**（`ingredients` 1136/1525 非空、`forms` 1255/1525 非空、`flavors` 只有 497/1525 非空）
  - 全表只有 **1084 / 1525** 行能匹配到至少一个 siblings，**441 行永远显示"无对照"**
  - 三字段全非空的只有 391 行；抽样 `id=1`（mackerel/aburi/grilled）、`id=2`、`id=8` 的 siblings 全是 **0**
- **两个具体坑**：
  1. `NULL = NULL` 在 SQL 里永远不成立，所以任一字段为 `NULL` 的行必然 0 对照（空串 `''` 之间反而会互撞，把不同菜并成一组）
  2. 跨语言写法匹配不上：台湾写 `mackerel`、日本可能写 `saba`，`=` 认不出是同一道菜 —— 而"七地区比价"正是这个页面的卖点
- **修法方向**：改用 `COALESCE(col,'') = COALESCE(?,'')`，并考虑用「配料集合」而不是整串相等（例如按拆分后的 token 做交集打分）。

### BUG-6 `/api/dishes` 无分页，一次 135 KB

- **实测**：`GET /api/dishes` 返回 **135008 字节**（271 道全量）。
- 前端 `menu.vue`（`PAGE_STEP=60`）和 `encyclopedia.vue` 都用 `slice` 做**纯前端**增量渲染兜住了 UI 卡顿，但**首屏仍要下载全量**；世界菜单那边前端是真的分页（`limit/offset`，一次 60 条），两边不一致。
- **修法方向**：给 `/api/dishes` 加 `limit/offset`，前端改成真分页。

### BUG-6 `/api/dishes` 服务端分页

### BUG-10 口味统计改为按菜品计

- 原实现按「标签出现次数」计数，一道菜挂 2 个喜欢标签就算 2 次（meal 1 `likeHit=4` 但 `matchedItems=3`）。
- 改法：每道菜先算 `hasLike` / `hasDislike`，两者都没有就跳过；`prefTotal++` 后忌口优先（`hasDislike` → `dislikeHit++`，否则 `likeHit++`）；`prefRatio = prefTotal > 0 ? likeHit / prefTotal : 0.5`。`basis` 同步加 `prefTotal` 与 **`prefCountMode: 'per-dish'`** —— 这样更早写下的那几条「按标签次数」的旧记录，能在数据里一眼区分出来。
