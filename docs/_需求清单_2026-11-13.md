## 2. 热量上限达不到 80% —— **确认是真问题，已复现，根因在代码里**

### 实测（`_planfill.mjs`，只读，跑在真库上）

| 预算 | 热量上限 | 实得热量 | 达到上限 | 实付 |
|---|---|---|---|---|
| 40 | 400 | 175 | 44% | ¥38 |
| 40 | **800** | 175 | **22%** | ¥38 |
| 60 | 400 | 305 | 76% | ¥55 |
| 60 | **800** | 305 | **38%** | ¥55 |
| 80 | 400 | 325 | 81% | ¥80 |
| 80 | **800** | 325 | **41%** | ¥80 |
| 80 | **1200** | 325 | **27%** | ¥80 |
| 120 | 600 | 573 | 96% | ¥119 |
| 120 | 800 | 755 | 94% | ¥116 |
| 120 | 1500 | 895 | 60% | ¥119 |

**看这三行的对比**：预算 80 时，不管上限填 400 / 800 / 1200，拿到的都是 **325 kcal**。

### 根因（`backend/src/recommend.js`）

热量上限目前**只是「天花板」，不是「目标」**：

- `:32`、`:54`、`:85` —— 三处都只判 `totalCal + c > calLimit → 跳过`，**从来不做「还差多少」的判断**
- `:80` 和 `:91` —— 唯一的推进条件是 **价格**：`if (totalPrice >= b * 0.95) break;`
- `:45` —— 排序是「偏好分 → 价格」，**完全不含热量**
- `:77` —— 补份数只补 3 轮，且每轮都被价格门槛卡住

所以：**预算先用完，计划就停**；热量落在哪里纯粹是巧合。上限松的时候（大家常用的就是松的），热量就随缘。

上限紧的时候反而正常（96% / 94%），因为天花板真的卡住了 —— 这也解释了为什么有时看着对、有时差很多。

### 成员提的三个改法，都对得上

| 成员的说法 | 对应改法 |
|---|---|
| 热量改成区间选择 | 把 `calorieLimit` 一个上限，改成 `calorieMin ~ calorieMax`；`calorieMin` 给生成器一个「目标」 |
| 多几个组合方案 | 现在只出一套（一个预算一个上限一个结果）。改成一次出 3 组，目标不同：**省钱 / 吃饱 / 均衡** |
| 购物车里菜的热量计算 | 点单卡/购物车逐条显示 kcal + 合计 kcal（后端 `unit_calories` 字段本来就有，前端没展示全） |

**建议的最小改法**：`recommend.js` 里加一个「二次填充」阶段 —— 贪心结束后，如果 `totalCal < calorieMin` 且预算还有剩，就按 **kcal/元 从高到低** 继续加菜，直到够到 `calorieMin` 或预算用完。这样不改数据结构，只改填充策略。

补一个事实：热量最高的菜是 **天婦羅綜合拼盤 ¥18 / 1490 kcal**（82.8 kcal/元），其次是叉燒豚骨拉麵 ¥31 / 1260、牛肉烏龍麵 ¥25 / 1180。所以在预算 40 里想凑到 400 kcal，只要允许选到炸物就够了 —— **现在选不到，正说明排序里没有热量维度**。

## 3. 用餐人数 + 茶位费 —— **这两个功能目前根本不存在，是新增，不是修 bug**

全项目搜过（`frontend/` + `backend/`，`.vue`/`.js`）：

```
人数     0 处
茶位     0 处
diners   0 处
person   0 处
people   0 处
guests   0 处
seat     0 处
```

**没有任何「用餐人数」输入，也没有任何「茶位费/人头费」计算。** 所以「加了人数导致茶位费异常」这句里的两样东西现在都没有 —— 成员看到的异常，可能来自别的地方（比如把「预算」当成了人均，或者把他自己算的账对不上）。

**这其实是好事**：不用改坏的，直接设计对。要做的话是：

1. `plan.vue` 加「用餐人数」输入
2. 预算语义说清楚：**总额** 还是 **人均**（这是最容易出岔子的地方）
3. 茶位费：本店实际有没有这一项要确认；有的话按人数乘，加在预估里，并且**在点单卡上单独列一行**，不要混进菜品合计
4. 「点菜过敏提示」：现在 `record.vue` 有过敏原输入，但**没有在点单卡/确认页面对已选菜品做过敏原校验提示** —— 这个是真缺的，而且比茶位费重要

## 4. UI 动图 —— 可做，注意小程序的成本

能做，但要挑对形式。小程序里 `lottie`（`lottie-miniprogram`）或纯 CSS 动画都行，**不要引大动图资源**（包体积之前刚从 524 KB 压到 115 KB）。

性价比高的三处：

| 位置 | 动效 | 成本 |
|---|---|---|
| 生成套餐按钮 | 点击 → 加载时按钮内一个循环动效 | 低 |
| 结果页出现 | 卡片依次淡入上移（错开 60ms） | 低 |
| 图鉴解锁 | 新解锁的格子一个高亮 sweep | 中 |

关于「参考麦当劳小程序」：可以看它的动效节奏和缓动曲线（该类品牌小程序动效普遍是 200–300ms、`ease-out`），**但直接扒素材/图标有版权问题**，节奏可以学，图不能抄。

## 5. 儿童套餐模式 —— 新增，规模中等

要做的话不是加个筛选就完事，至少要定四件事：

1. **触发方式**：计划页一个「儿童模式」开关？还是独立的入口？
2. **约束是什么**：低辣/无生食/小份/价格低/热量低 —— 现在数据里有 `raw`（生熟）字段可用，辣度**没有**字段
3. **份数口径**：儿童套餐算 1 人份还是按人数乘
4. **展示**：结果页要不要单独标题和文案

数据层能支撑的部分：`dishes` 有 `raw`（生/熟）、`calories`（271 道全有）、`price`、`tags`。缺的是「辣」和「份量大小」两个维度 —— 要补的话是加字段，**数据库只能加数据**，加列需要单独确认。

## 6. 我的额外发现（不在成员清单里，但影响第 2 条和第 1 条）

### 在售菜品里有 156 道是重复的

```
在售 269 道 → 78 组同名重复 → 涉及 156 道（58%）
```

同一组里 **名字、价格、热量、创建时间全都一样**，只有 `category_id` 不同：

| id | 名称 | category_id | 价格 | 热量 |
|---|---|---|---|---|
| 299 | 花壽司 | 8 | 23.0 | 90 |
| 394 | 花壽司 | **11** | 23.0 | 90 |
| 374 | 泡菜 | 11 | 11.0 | 280 |
| 415 | 泡菜 | **14** | 11.0 | 280 |

这会影响：
- **计划生成器**：贪心循环（`recommend.js:52`）把每一行当成一道不同的菜，理论上同一道菜能被选中两次
- **菜单页**：271 道里一大半是重复项，翻页看着像重了
- **图鉴**：目标数 269 是被重复灌大的，解锁进度看着比实际少

**但是不能删**（违反「数据库只能加数据」）。可行的做法是**在查询层按 `name` 去重**（同名只取 id 最小的那条），代码改、库不动。

### 数据质量其它两条

- `dishes.calories` 271 道全有值（之前补过 249 条），但**热量的可信度不一**：`天婦羅綜合拼盤` 1490 kcal 明显是整份拼盘，`乌龙茶` 0 kcal 是对的，`抹茶` 5 kcal 偏低
- `world_dishes` 1525 道里 **1031 道有图且文件都在**（一条不差）；印尼 272 + 马来 152 完全没有图片路径；新加坡 136 道里有 70 道没图

### 实际做法（原计划没写的两处）

1. **热量补足改成「贴住上限」而不是「够到下限」**。第一版按下限 80% 收手，填 300–500 会在 305 就停（只用了 61% 的额度）。改成一直补到上限为止，下限只用来判断「有没有进到你点的区间」。
2. **给同一道菜加了 2 份上限**。不加的话，凑预算的最后一步会把便宜菜反复叠份 —— 实测出现过「4× 乌龙茶 + 5× 抹茶」这种把 ¥64 花在饮料上的组合。
3. **候选集按菜名去重**。叠份上限加上后仍有 3 例出现 3 份，查出来是**库里的同名重复菜**（同一名字两个 id 各 2 份），所以又补了按名去重。

### 无法填满的情况（诚实记录）

预算 30–40 元配 1200/1500 kcal 这种组合，最初无论怎么排都只能到 55%：3b 的换菜是「一对一」的，预算花光时只能拿一份换价格相近的一份，买不起「贵一点但热量高得多」的菜（篮子里全是 7 kcal/元的蒸蛋和味噌汤，换不动 ¥18 / 1490 kcal 的天婦羅拼盤）。
后面加了 **3c**：填不到目标的 80% 时，按「每块钱热量」重排整篮再比一次，谁热量高用谁。加完之后 77 组扫描里**没有一组低于 80%**。

去重保留的是 **id 最小**的那一份（已断言校验）；进度按**菜名**合并 —— 吃过同名的任意一份，那一格就算解锁，所以已解锁 5 道不变。

### 第 4 条：一次出三套方案（省钱 / 均衡 / 吃饱）

三套共用同一套候选集与同一条流程，差别只在三个开关：

| 方案 | 怎么排 | 收手条件 | 同一道菜 |
|---|---|---|---|
| **省钱** | 按「每块钱热量」从高到低拿 | 够到目标热量（上限的 80%）就停 | 1 份 |
| **均衡** | 偏好优先，再做补足 | 补到上限的 **90%** | 最多 1 份 |
| **吃饱** | 偏好优先，再做补足 | 一直补到贴住上限 | 最多 2 份 |

- 后端：`generatePlan` 新增 `strategy` 与 `dryRun` 两个选项；`dryRun=true` 时整段跳过落库，返回的 `planId` 为 `null`。
- 新增 `POST /api/plans/suggest`：同一预算与热量区间，三套各算一次（都 dryRun），返回 `{ variants: [{key,label,hint,ok,error,plan}], usable }`。三套都排不出来时返回 400。
- 前端 `plan.vue`：多一个「一次看三套」按钮；三张卡片各显示价格 / 热量 / 达到上限的百分比 / 菜品列表，卡片底部是「用这套」—— 点了才带着那个 `strategy` 调 `/api/plans/generate` 真正落库，然后自动刷新历史计划。
- **为什么对比时不落库**：三套都写进 `meal_plans` 会让「历史计划」每次多三行垃圾。先看、再选、最后才存。

实测（`_variants.mjs`，跑真库）：

| 预算 / 区间 | 省钱 | 均衡 | 吃饱 |
|---|---|---|---|
| 80 / 800 | ¥23 · 790 kcal · 1 道 | ¥72 · 770 kcal · 6 道 | ¥80 · 800 kcal · 6 道 |
| 40 / 1500 | ¥18 · 1490 kcal · 1 道 | ¥39 · 1210 kcal · 3 道 | ¥34 · 1500 kcal · 2 道 |
| 60 / 不给上限 | ¥55 · 305 kcal · 5 道 | ¥55 · 305 kcal · 5 道 | ¥55 · 305 kcal · 5 道 |

- **「省钱」在 ¥23 就拿到 790 kcal**（一道 鮮蝦天滿滿），因为它是「用最少的钱够到目标热量」，不是「偏好优先」。
- **不给热量上限时三套一样**：此时「省钱」只表示「不做后续补足」，不换序 —— 换序会变成「按热量密度优先」，实测预算 60 能拼出 3060 kcal 的一桌，荒谬。
- 落库检查：调 `/api/plans/suggest` 前后 `meal_plans` 条数不变（dryRun 生效）；调带 `strategy` 的 `/api/plans/generate` 后 +1（确实落库）。
- 回归：不传 `strategy`、不给上限时仍是 ¥55 / 305 kcal / 5 道，与改动前逐字相同。

#### 补记：三套一样时的界面提示（2026-11-13 晚，实测后加的）

在模拟器里点「一次看三套」时发现：**没填热量上限的话，三张卡片一模一样**（都是 ¥120 / 1265 kcal / 13 道）。功能没坏 —— 三套的差别全在「热量目标」这一个变量上，没有目标时 `value` / `balanced` / `full` 就退化成同一种点法。但界面上看起来像按钮坏了。

处理（`frontend/pages/plan/plan.vue`）：

- 新增 `variantSpread` computed：把三套的「菜品 id × 份数」排序拼成签名，再去重比较。全同则 `'same'`，否则 `'diff'`（不足两套有效时 `'none'`，不提示）。
- `'same'` 时在三套卡片上方显示一条浅黄提示：「这次三套算出来是一样的 —— 三种策略的差别全在「热量目标」上，没填上限时它们就退化成同一种点法。填个区间再比一次就能看出区别。」
- 提示里带一个「用『正常 500–700』再比」的按钮，调 `fillRangeAndCompare()`：套上预设再重算一次。**不默认替用户填区间** —— 热量区间是用户的决定，不能悄悄改掉输入。

模拟器实测（CDP 点「一次看三套」→ 再点那颗补区间的按钮）：

| 时刻 | 输入框（预算/下限/上限） | 三套结果 |
|---|---|---|
| 不填区间 | `80 / 空 / 空` | 三套完全相同（325 kcal、6 道），并显示那条提示 |
| 点过按钮后 | `80 / 500 / 700` | 省钱 ¥22 · 650 kcal · 93% · 2 道（醬油團子 / 海苔味噌湯）；均衡 ¥77 · 675 kcal · 96% · 6 道；吃饱 ¥79 · 700 kcal · 100% · 5 道 |

提示条在补完区间后自动消失（`variantSpread` 变 `'diff'`），不需要手动关。

### 第 5 条：用餐人数 + 茶位费

- 这一段**没动后端、没动数据库**（`meals` 表不加列），全部在 `frontend/pages/record/record.vue` 里。
- 「用餐人数」1–12 的步进器；给了人数就顺手把来自推荐计划的预算与热量上限**按人头拆一份**（`人均预算 ¥X · 人均热量 Y kcal`）。
- 「茶位费 / 服务费（每位）」输入框，**默认空 = 0**，下面直白写清：
  > 这家店收不收茶位费我们没有依据，所以默认 0 —— 按实际小票填，填了才会算进下面的合计，不会自动给账单加钱。
- 填了茶位费才出现合计行：`菜品 ¥A + 茶位费 ¥B（N 人 × ¥C）= ¥D`，后面一个「填入」把 D 写进「账单实付」输入框。
- **为什么不自动算进实付**：项目有一条硬性的数据真实性规则，我们没有这家店收茶位费的任何凭据。所以只提供算术与一键填入，**不替用户决定金额**。

### 体检采样的一个坑（会影响你判断「是不是坏了」）

`_appcheck3.mjs` 切页后只等「页框出现 + body 文本非空」，**文本一出现就读，数据可能还没回来**。所以同一份代码连跑两次，`history` 可能是 `共 4 条记录`（113 字）也可能是 `共 0 条记录 加载中…`（12 字），`admin` 可能是 9747 字也可能是 72 字（`菜品管理（0）`）。
判定方法：**同一页多跑一次**，或直接打接口 —— 实测 `/api/meals` 200 有 4 条、`/api/dishes?status=on_sale,pending,off_sale` 200 有 271 条、`/api/categories` 16、`/api/tags` 18、`/api/badges` 27，接口侧全部正常。**不是缺陷。**

### 第 6 条：UI 动效

节奏参考麦当劳那类快餐点单小程序（240–320ms、ease-out、位移 8–14rpx、不弹跳），但**素材一张没扒**，全是 CSS。

`frontend/App.vue` 顶部加三条关键帧与四个通用类，任何页面加个 class 就能用：

| 类 | 效果 | 用在哪 |
|---|---|---|
| `.anim-card` | 整卡上浮淡入 280ms | 计划结果卡 |
| `.anim-pop` | 缩放淡入 260ms | 三套对比卡片、图鉴已解锁格子 |
| `.anim-list` | 子项按序号错开 40ms 进场（最多 8 项） | 首页「最近用餐」、计划结果里的菜品行 |
| `.anim-pulse` | 透明度呼吸 1.1s 循环 | 计算中的按钮 |

- **不引任何图片/GIF**：小程序包好不容易从 536 KB 压到 115 KB，加 GIF 会十几倍地还回去。
- 错开进场只做前 8 项 —— 再往后延迟加起来会超过 1 秒，反而显得卡。

### 第 7 条：儿童套餐模式

## 9. 健康目标（减重 / 控糖 / 轻食）—— 问卷第 3 题第 21 条的落地

### 为什么做这个

问卷第 3 题（开放式建议，29 条）里，第 21 条是一段英文长答，写得最具体：

> The feature I want most is **healthy meal planning packages**. The app can provide **grouped meal options for people with different needs, like weight loss, blood sugar control or light diet**. It would be much easier for these users to pick restaurants and dishes that match their health goals.

29 条里按主题归类（8 条「无 / 没有」、1 条「不怎么用小程序」不算建议，**有效 20 条**）：

| 主题 | 条数 | 条目 |
|---|---|---|
| 排队 | **4** | 1 线下还要取号 · 7 排号 · 10 实时排队提醒 · 27 快到号自动推送 |
| **健康 / 热量** | **4** | 14 热量查询 · **21 按减重/控糖/轻食分组** · 23 合理价格吃出身材 · 28 卡路里测量 |
| 价格透明 | 3 | 3 看新品与价格 · 22 价格更透明 · 26 折扣 |
| 过敏原 / 成分 | 2 | 20 过敏原详细标注 · 29 优化食物做法告知 |
| 信息架构 | 2 | 5 找东西麻烦 · 19 点单 |
| 各 1 条 | 5 | 11 抹茶奶难喝 · 15 路线规划 · 17 多人分单 · 18 服务器卡 · 25 消费评价 |

**最高频的「排队」反而是我们不该做的**：那是寿司郎官方小程序已有、且需要门店实时队列数据的能力，我们凭空造就是假数据。它反过来印证了定位 —— 补官方缺的三件事：预算、热量、过敏。健康目标这一条是剩下里最值得做的。

### 数据边界（决定了设计）

库里能用的信号只有两样：

- `dishes.calories` —— 271 道**全部有值**（2026-11-09 从 `dish_nutrition` 补齐 249 条）
- `dish_tags` —— 18 个标签，`ingredient` 13 个（三文鱼 / 金枪鱼 / 虾 / 鸡蛋 / 小麦 / 乳制品 / 油炸 / 生食 / 黄瓜 / 牛油果 / 蟹肉 / 鳗鱼 / 海苔）、`flavor` 5 个（鲜 / 甜 / 咸 / 酸 / 苦）

**没有糖分、没有蛋白质、没有钠、没有膳食纤维**。所以不写「低糖」「高蛋白」这种话 —— 那会变成编数据。

### 做了什么（不改数据库、不加列）

`backend/src/recommend.js` 新增 `GOAL_RULES`，三档各做两件事：

| 目标 | 默认热量区间 | 排除标签 | 因这条规则排掉 |
|---|---|---|---|
| `weight_loss` 减重 | 500–700 kcal | 油炸（tag 7） | **27 道** |
| `blood_sugar` 控糖 | 400–600 kcal | 甜味（tag 15） | **5 道** |
| `light` 轻食 | 300–500 kcal | 油炸（tag 7） | **27 道** |

两个关键取舍：

1. **只在用户没填热量区间时才套默认值**。用户填了就以用户的数为准 —— 返回里有个 `goalRangeApplied` 字段说明这次到底套没套，不让它暗中生效。
2. **不给「减重」排碳水、不给「控糖」排油炸**。前者库里分不出主食（寿司的饭和刺身的区别不在标签里），后者是脂肪不是糖，硬排等于编。

**排除量记在返回值里**：`goalNote` 写「按「油炸」标签排除了 27 道菜；这不是营养学判定，是标签推断。」—— 代价摆在明面上，不是悄悄少给。

### 控糖这一档必须说清的事

界面上一共有三处警示，都是同一个意思：

1. 选择器下方 `goalHint`：「⚠ 这里只有甜味标签，没有糖分数据 —— 咸味菜里的隐形糖判不出来，糖尿病人请以店家与医生为准。」
2. 结果卡 `.goal-box` 里 `goalNote`：按哪个标签排的、排掉几道
3. 结果卡 `plan.goal === 'blood_sugar'` 时多一行 `.goal-warn`：「我们只有「甜味」标签，没有糖分数据。咸味菜里的隐形糖、标了无糖但含淀粉的菜，这套都判不出来。」

**为什么敢做这一档**：5 道甜味菜（玉子烧寿司 / 鳗鱼寿司 / 甜虾刺身 / 抹茶冰淇淋 / 红豆和果子 / 可乐）确实是控糖时最先该避的，排掉它们比不排有用。但它只是「先避最明显的」，不是「算过含糖量」。

## 10. 历史计划的服务端分页（2026-11-13 晚，验收时发现的）

### 怎么发现的

把 11 个接口的响应体积挨个量了一遍：

| 接口 | 大小 | 条数 |
|---|---|---|
| **`/api/plans`** | **192 601 B** | **505** |
| `/api/dishes` | 164 845 B | 271 |
| `/api/dishes?dedupe=1` | 116 912 B | 193 |
| `/api/encyclopedia` | 39 429 B | 191 |
| `/api/world/dishes?limit=60` | 19 110 B | 60 |
| `/api/ingredients` | 7 408 B | 98 |
| `/api/badges` | 6 558 B | 27 |
| `/api/meals` | 1 063 B | 4 |
| `/api/tags` | 1 070 B | 18 |
| `/api/categories` | 972 B | 16 |
| `/api/allergens` | 680 B | 14 |

`/api/plans` 是唯一**随历史无限增长**的 —— 每生成一次计划就多一条，永远不会收敛。
505 条时 192 KB，演示当天如果再多点几下，这个数字还会上去，而且前端一次性全渲染。

### 改法（与 `/api/dishes` 同一套约定，不破坏老调用方）

`backend/src/routes.js` 的 `listPlans`：

```js
const limit = Math.min(Math.max(Number(query.limit) || 0, 0), 5000);
const offset = Math.max(Number(query.offset) || 0, 0);
const total = db.prepare('SELECT COUNT(*) AS n FROM meal_plans WHERE user_id=?').get(user.id).n;
const sql = `SELECT p.*, (SELECT COUNT(*) FROM meal_plan_items WHERE meal_plan_id=p.id) AS item_count
               FROM meal_plans p WHERE p.user_id=? ORDER BY p.id DESC` + (limit ? ' LIMIT ? OFFSET ?' : '');
```

**关键：`limit` 为 0 时根本不给 SQL 加 `LIMIT`** —— 所以没传 `limit` 的老调用方，返回的
`plans` 数组与以前逐字相同（只是多了 `total` / `limit` / `offset` 三个字段）。

`frontend/pages/plan/plan.vue`：`loadHistory(reset = true)` 带 `?limit=20&offset=`，
往下翻时 `offset = history.value.length` 并 `concat`；标题的「（N）」改成用 `total` 而不是
`history.length`，否则分页后永远显示 20。老后端没有 `total` 时退化成「已拿到的条数」，不会显示虚假的更多。

### 实测

| 请求 | 响应 | 条数 | total | limit | offset |
|---|---|---|---|---|---|
| `/api/plans` | 192 636 B | 505 | 505 | 505 | 0 |
| `/api/plans?limit=20&offset=0` | **7 706 B** | 20 | 505 | 20 | 0 |
| `/api/plans?limit=20&offset=20` | 7 706 B | 20 | 505 | 20 | 20 |
| `/api/plans?limit=20&offset=500` | 1 978 B | 5 | 505 | 20 | 500 |

**首屏载荷降 96%**（192 KB → 7.7 KB）。模拟器实测：计划页历史计划区显示 `历史计划（505）`，
首屏 20 条，末行 `加载更多（20/505）`。

## 11. 「全部完成」这一轮另外核到的两件事

### 一、12 页体检工具的采样漏洞已修

旧版 `_appcheck3.mjs` 只等「页框出现 + body 文本非空」就读，数据可能还没回来，于是出现
`history` 读到「共 0 条记录 加载中…」（12 字）、`admin` 读到「菜品管理（0）」（72 字）这类假阴性。

新版 `_appcheck4.mjs` 改成 **文本长度连续 3 次不变才算渲染完**（`stable >= 2`，上限 26 秒），
于是 **12/12 全 hit、运行时异常 0** —— 包括长期被判 MISS 的 `mealDetail?id=4`。
那个 MISS 从来不是页面缺陷，是采样太早。
